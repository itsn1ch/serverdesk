# Isolated Generated SSH Configuration and Static Configuration Import

Status: needs-info
Source: ADR-0002; ADR-0001 and ADR-0003 at their transport/trust boundaries; product specification v2.1 §§2.1, 4.1, 4.3–4.7, 4.10, 5.2, 6.1, 7.1, 12, 13, 14, 16, 17 and 18; GLOSSARY.md.

## Problem Statement

A Developer managing personal Linux Servers needs to reuse connection settings without granting a configuration file permission to execute local commands or override the application's Host Key policy.

The user's SSH configuration can contain `Match exec`, `ProxyCommand`, `KnownHostsCommand`, `LocalCommand` and `Include` directives with effects beyond selecting connection values.

Even `ssh -G` can execute `Match exec`, so passing additional options on top of the user's configuration does not establish runtime isolation.

Configuration import must create an application-owned inventory snapshot, not an ongoing dependency on the original file or an implicit Host Key Adoption workflow.

## Solution

Generate runtime SSH configuration from inventory and Auth Profiles for each Connection Identity, and launch every master with `-F` selecting that generated configuration.

Force the accepted Host Key, local-command and control-connection security options rather than permitting imported settings to override them.

Read the user's configuration only through an explicit static Rust parser with the accepted whitelist, report unsupported content with reasons and never evaluate that content through OpenSSH or a shell.

Represent imported ProxyJump routes as Jump Servers registered in inventory.

Use `ssh -G` only to self-check generated configuration, including detecting unregistered proxy routes.

Preserve original files and keep re-import/diff and recursive Include import outside this epic.

## User Stories

### Inventory-backed runtime configuration

1. **US-001: Generate configuration from the saved Connection Identity**

   - **Story:** As a Developer managing personal Linux Servers, I want each connection to use the inventory and Auth Profile I selected rather than unrelated settings in my user SSH configuration, so that I can predict the destination and authentication context used at runtime.

   - **Basis:** Derived: ADR-0002; product §§4.1, 4.3, 4.4, 4.5 and 13.1; glossary Connection Identity and Auth Profile.

   - **Acceptance criteria:**
     - **US-001-AC1:** Given a saved Connection Identity, when its runtime configuration is generated, then the effective host, port, SSH user, complete Jump Server route and authentication context come from the saved inventory and referenced Auth Profile.
     - **US-001-AC2:** Given the Auth Profile selects an agent or key reference, when the configuration is generated, then the corresponding `IdentityAgent`/`IdentityFile` settings express those references without adding a password, passphrase or other secret to configuration or SQLite.
     - **US-001-AC3:** Given two Server entries share a Connection Identity, when they are used, then configuration respects ADR-0001's single-master sharing boundary rather than treating inventory display names as separate authentication contexts.
     - **US-001-AC4:** Given a different host, port, user, Jump Server route or authentication context is selected, when that identity is connected, then its configuration does not accidentally inherit the different identity's endpoint, route, key/agent reference or control socket.

2. **US-002: Force the application's runtime security policy**

   - **Story:** As a Developer managing personal Linux Servers, I want imported or external configuration to be unable to weaken Host Key checks or execute local commands during a connection, so that I can connect without allowing imported settings to bypass the application security boundary.

   - **Basis:** Derived: ADR-0002; product §§4.3, 4.4, 4.6, 4.7 and 4.10; ADR-0001 and ADR-0003.

   - **Acceptance criteria:**
     - **US-002-AC1:** Given a master starts, when its effective configuration is inspected and exercised, then `StrictHostKeyChecking=yes` is enforced and an unaccepted or mismatched Host Key cannot be accepted implicitly by SSH.
     - **US-002-AC2:** Given Host Key material has been generated by ADR-0003, when SSH checks Host Keys, then `UserKnownHostsFile` selects that generated file and `GlobalKnownHostsFile=none` excludes global Host Key files; user Host Key files are not runtime sources of trust.
     - **US-002-AC3:** Given a connection starts, when its effective policy is exercised, then `KnownHostsCommand=none` and `PermitLocalCommand=no` prevent external Host Key command lookup and permitted local-command execution.
     - **US-002-AC4:** Given a remote Server advertises additional Host Keys, when the connection is used, then `UpdateHostKeys=no` prevents SSH from silently changing the application's accepted Host Key material or Trust State.
     - **US-002-AC5:** Given a Connection Identity is connected, when control options are resolved, then `ControlMaster` and `ControlPath` remain explicitly application-owned and identify the master/socket required by ADR-0001 rather than a master selected by user configuration.
     - **US-002-AC6:** Given the application disconnects or terminates, when control persistence is evaluated, then `ControlPersist=no` is enforced and generated policy does not deliberately keep an independently persisting master alive.
     - **US-002-AC7:** Given imported content requests different trust files, local commands, Host Key update behavior or control options, when the imported inventory is later connected, then the forced options above remain effective and the excluded source options do not override them.

   - **Dependencies:** US-001.

3. **US-003: Isolate every master and consumer from user configuration**

   - **Story:** As a Developer managing personal Linux Servers, I want terminal, file, administrative and monitoring connections to use the same isolated runtime policy, so that I receive consistent protection regardless of which feature opens a channel.

   - **Basis:** Derived: ADR-0001 and ADR-0002; product §§4.4, 4.7, 5.2, 6.1 and 7.1.

   - **Acceptance criteria:**
     - **US-003-AC1:** Given the application starts a master, when system OpenSSH is invoked, then `-F` selects generated configuration for that Connection Identity and `~/.ssh/config` is not read or evaluated at runtime.
     - **US-003-AC2:** Given terminal, SFTP, Operation and Collector consumers use the connection, when they run, then they retain the generated configuration/control-master boundary rather than falling back to the user's SSH configuration or independently resolving the destination from it.
     - **US-003-AC3:** Given the user's configuration contains an executable `Match exec`, `ProxyCommand`, `KnownHostsCommand` or `LocalCommand`, when application connection workflows run, then none of those source-file commands executes, whether it is in the directly named file or reachable through an Include tree.
     - **US-003-AC4:** Given the original configuration is edited, removed or contains contradictory endpoint/authentication values after import, when the existing inventory snapshot is used for a connection, then those external changes do not alter its effective runtime configuration.
     - **US-003-AC5:** Given a consumer cannot attach to the intended configured connection, when it reports failure, then it does not silently create an alternate connection governed by external configuration.

   - **Dependencies:** US-001, US-002.

4. **US-004: Use only registered Jump Server routes**

   - **Story:** As a Developer managing personal Linux Servers, I want a proxy route to identify the actual inventory Jump Servers I selected rather than an executable or hidden route from an external file, so that I can understand and control every hop used to reach the target.

   - **Basis:** Derived: product §§4.1, 4.3, 4.4, 4.6 and 4.10; glossary Jump Server; ADR-0001 and ADR-0003.

   - **Acceptance criteria:**
     - **US-004-AC1:** Given a direct or multi-hop connection route is saved, when generated configuration represents it, then each Jump Server comes from registered inventory and the complete route contributes to Connection Identity.
     - **US-004-AC2:** Given a ProxyJump value is imported, when it becomes usable connection configuration, then it is represented as a route through Jump Servers in inventory rather than an opaque user-config alias resolved at runtime.
     - **US-004-AC3:** Given a route cannot be represented using registered Jump Servers, when Connect or the generated-configuration self-check encounters it, then it is rejected as `UnregisteredProxyRoute` rather than executed as an external command or silently omitted to make a direct connection.
     - **US-004-AC4:** Given a registered route is otherwise usable but a Jump Server fails the ADR-0003 trust gate, when connection is requested, then configuration registration alone does not authorize its use and the connection remains blocked by that gate.
     - **US-004-AC5:** Given a usable registered route, when actual connection traffic is exercised, then it reaches the configured target through the registered Jump Servers, with no extra route introduced by the user's SSH configuration.

   - **Dependencies:** US-001, US-003.

5. **US-005: Self-check only generated configuration**

   - **Story:** As a Developer managing personal Linux Servers, I want configuration self-checks to expose unsafe routes without executing commands from the file I am importing, so that I can validate configuration without granting the source file execution privileges.

   - **Basis:** Derived: ADR-0002; product §4.4 and §16.1.

   - **Acceptance criteria:**
     - **US-005-AC1:** Given the application uses `ssh -G`, when it performs a self-check, then its only configuration input is the application's generated configuration, never the original user configuration or an Include tree from it.
     - **US-005-AC2:** Given a generated configuration self-check reveals a proxy route that is not registered in inventory, when the check completes, then connection is rejected with `UnregisteredProxyRoute` rather than treating `ssh -G` output as authorization to use that route.
     - **US-005-AC3:** Given a configuration is imported, when its settings are inspected or resolved for import, then neither `ssh -G` nor another OpenSSH evaluation of the source file is used as the parser.
     - **US-005-AC4:** Given generated configuration cannot be produced or its required checks fail, when connection is requested, then the workflow reports the configuration/storage failure and does not bypass the failure by reading the user's configuration or launching an unchecked fallback connection.

   - **Dependencies:** US-001, US-004.

### Explicit static import

6. **US-006: Parse a configuration snapshot without executing it**

   - **Story:** As a Developer managing personal Linux Servers, I want to explicitly import supported connection settings while remaining in control of local configuration files and remote connection attempts, so that I can reuse connection settings without implicitly starting connections or adopting external behavior.

   - **Basis:** Derived: ADR-0002; product §§4.1, 4.4, 4.10, 12 and 18.

   - **Acceptance criteria:**
     - **US-006-AC1:** Given the Developer explicitly invokes import for `~/.ssh/config`, when the source is read, then Rust statically parses the file without executing commands, opening SSH connections or invoking OpenSSH to evaluate the file.
     - **US-006-AC2:** Given supported entries are imported successfully, when they are displayed, then they exist as saved inventory/Auth Profile settings rather than live references whose values depend on re-reading the original configuration at connection time.
     - **US-006-AC3:** Given the original file contains a mixture of supported and unsupported content, when import reports its result, then the Developer can distinguish the settings imported from the entries/directives not imported and see the reason for each exclusion.
     - **US-006-AC4:** Given a Server is saved through import without an explicit connection request, when import finishes, then it can remain disconnected; importing settings is not proof of connection or Host Key trust and does not bypass the default `connect_on_startup=false` behavior.
     - **US-006-AC5:** Given source values contain text that resembles a command, when import and later connection run, then data cannot cause the importer to execute that text or emit excluded executable directives into generated configuration.

   - **Dependencies:** US-001.

7. **US-007: Import only the accepted static whitelist**

   - **Story:** As a Developer managing personal Linux Servers, I want supported SSH settings to become understandable application settings without importing unrelated OpenSSH behavior, so that I can retain useful connection values while excluding unsupported semantics.

   - **Basis:** Derived: product §4.4; ADR-0002; glossary Auth Profile and Jump Server.

   - **Acceptance criteria:**
     - **US-007-AC1:** Given statically supported HostName, Port and User settings, when import succeeds, then the saved connection settings and a subsequent actual connection use their imported endpoint and SSH user values.
     - **US-007-AC2:** Given statically supported IdentityFile and IdentitiesOnly settings, when import succeeds and the saved configuration is used, then those settings are represented as non-secret key/authentication references and honored without importing key material or a passphrase into SQLite.
     - **US-007-AC3:** Given a statically supported ProxyJump setting, when import succeeds, then it contributes the corresponding registered inventory Jump Server route under US-004 rather than a runtime dependency on a source-file alias.
     - **US-007-AC4:** Given statically supported key-algorithm or cipher settings, when they are imported, then a subsequent generated configuration can use those allowed algorithm/cipher choices without permitting them to override the forced Host Key and local-execution policy.
     - **US-007-AC5:** Given any directive outside HostName, Port, User, IdentityFile, IdentitiesOnly, ProxyJump and the accepted key-algorithm/cipher category, when import examines it, then it is excluded with a reason even if OpenSSH normally recognizes that directive.
     - **US-007-AC6:** Given a source value is unsupported or cannot be represented in accepted inventory/Auth Profile settings, when import finishes, then that value is not presented as successfully imported or silently turned into an executable directive, and the exclusion is reported.

   - **Dependencies:** US-004, US-006.

8. **US-008: Report unsafe and dynamic directives without evaluating them**

   - **Story:** As a Developer managing personal Linux Servers, I want to see why dynamic configuration was skipped without the act of inspecting it triggering its side effects, so that I can understand import omissions without putting my workstation at risk.

   - **Basis:** Derived: ADR-0002; product §4.4 and §16.1.

   - **Acceptance criteria:**
     - **US-008-AC1:** Given a source contains a `Match` block, including `Match exec`, when import encounters it, then the block is reported as not imported with a reason, its condition is never evaluated and settings within that block are not imported as if they were unconditional values.
     - **US-008-AC2:** Given a source contains `Include`, when import encounters it, then the directive is reported as not imported with a reason and the importer does not read, expand, recursively import or evaluate the referenced file tree.
     - **US-008-AC3:** Given a source contains `ProxyCommand`, when import encounters it, then it is reported and skipped rather than executed or translated into a command-backed proxy route.
     - **US-008-AC4:** Given a source contains `KnownHostsCommand` or `LocalCommand`, when import encounters it, then each is reported and skipped and neither command executes during import, checking or connection.
     - **US-008-AC5:** Given a source contains other out-of-whitelist trust, control, agent or local-execution settings, when import encounters them, then they are reported and skipped rather than allowed to replace application-generated policy or Auth Profile choices.
     - **US-008-AC6:** Given all apparent connection values are inside unsupported dynamic blocks or Include trees, when import completes, then the result accurately reports that no supported connection settings were imported rather than fabricating a resolved OpenSSH configuration.

   - **Dependencies:** US-006, US-007.

9. **US-009: Preserve originals and keep configuration Import separate from Host Key Adoption**

   - **Story:** As a Developer managing personal Linux Servers, I want import to leave my existing SSH files untouched and avoid silently granting trust to imported destinations, so that I can preserve my existing setup and make Host Key trust decisions separately.

   - **Basis:** Derived: ADR-0002 and ADR-0003; product §§4.4, 4.6, 13.2 and 17; glossary Adoption and Trust State.

   - **Acceptance criteria:**
     - **US-009-AC1:** Given successful, partially supported or failed import input, when the workflow ends, then the original SSH configuration contents are unchanged and the application has not rewritten excluded directives or inserted generated settings into that file.
     - **US-009-AC2:** Given a connection setting has been imported, when the original file later changes, then the saved inventory snapshot does not change automatically and the UI does not imply that it tracks those external edits.
     - **US-009-AC3:** Given config Import has created a Server, when its Trust State is considered, then configuration import has neither read/adopted user `known_hosts` entries nor marked the Host Key `ADOPTED` or `VERIFIED`; those require the separate explicit ADR-0003 workflows.
     - **US-009-AC4:** Given the source contains an Include reference or is subsequently modified, when this epic's workflows are used, then no recursive Include import, automatic re-import or re-import/diff workflow is exposed as implemented functionality.

   - **Dependencies:** US-006.

### Failure and presentation boundaries

10. **US-010: Make import and configuration failures actionable without false success**

- **Story:** As a Developer managing personal Linux Servers, I want keyboard-accessible import results and configuration errors that identify what changed and what I can do next, so that I can recover from import or generation failures without confusing partial results with success.

- **Basis:** Derived: product §§2.1, 12.2, 12.3, 13.2, 14 and 18.

- **Acceptance criteria:**
  - **US-010-AC1:** Given the import surface and a result containing unsupported directives, when used with the keyboard, then import controls, exclusions/reasons and available error-recovery actions are reachable without a pointer.
  - **US-010-AC2:** Given source loading/parsing or configuration generation is in progress, when the Developer continues using the application, then the workflow exposes loading/progress without blocking GTK's main thread; presentation updates are delivered through `glib::MainContext` and Tokio never directly accesses GTK widgets.
  - **US-010-AC3:** Given the selected source has no importable settings, when parsing completes, then the view presents an accurate empty result with exclusions where applicable rather than a success claim for nonexistent Servers or an indefinite loading state.
  - **US-010-AC4:** Given the source cannot be read or contains a value that cannot be imported, when the failure is reported, then the UI identifies the affected source/entry, explains what failed and available actions, and does not claim the rejected settings were saved or that remote changes occurred.
  - **US-010-AC5:** Given local storage or generated-configuration creation fails, when the workflow reports its outcome, then it identifies the affected inventory/Connection Identity, accurately states what was or was not saved, exposes the appropriate storage/configuration error and does not claim a usable configuration or successful connection.
  - **US-010-AC6:** Given configuration failure affects an already presented workflow, when it is displayed, then the error identifies affected resources, whether changes may have occurred, available actions and applicable Operation details; any prior observation remains visibly stale rather than being presented as current success.

- **Dependencies:** US-005, US-006, US-008, US-009.

## Implementation Decisions

- Adopt ADR-0002's generated per-Connection-Identity configuration, selected explicitly with OpenSSH `-F`.
- Treat inventory and Auth Profiles as the runtime source of connection values; the user's SSH configuration will be an explicit static-import input only.
- Parse import input statically in Rust rather than evaluating it with OpenSSH, a shell or `ssh -G`.
- Preserve the accepted whitelist: HostName, Port, User, IdentityFile, IdentitiesOnly, ProxyJump, and key-algorithm/cipher settings.
- Exclude `Match` blocks, Include directives and all out-of-whitelist options with visible reasons rather than executing, resolving or recursively importing them.
- Convert ProxyJump settings into routes through registered inventory Jump Servers.
- Use `ssh -G` only as a self-check of generated configuration, including checking for unregistered proxy routes.
- Force `StrictHostKeyChecking=yes`, the generated `UserKnownHostsFile`, `GlobalKnownHostsFile=none`, `KnownHostsCommand=none`, `PermitLocalCommand=no` and `UpdateHostKeys=no`.
- Keep `ControlMaster` and `ControlPath` application-controlled and force `ControlPersist=no`, preserving ADR-0001's required master instead of disabling the master architecture.
- Obtain generated Host Key material and connection permission from ADR-0003; configuration import will not perform Adoption or Verification.
- Route terminal, SFTP, Operation and Collector consumers through ADR-0001's configuration-isolated connection lifecycle.
- Retain only authentication references, never secrets; importing settings will not add a Secret Service dependency.
- Preserve original configuration files and persist an inventory snapshot rather than a live external-file binding.
- Keep state ownership in the accepted layers: GTK presentation, application workflows and persisted inventory/Auth Profiles in SQLite; use main-context delivery for asynchronous presentation changes.

## Testing Decisions

The user approved the common test seam: presentation-facing application workflows backed by actual system OpenSSH and SQLite in isolated Incus/LXD Ubuntu 24.04 fixtures with systemd 255, real GTK smoke coverage, and narrow pure-behavior tests.

All tests here are planned; this documentation task does not create or execute a test harness.

- Pure-test static import with each whitelisted setting, mixed supported/unsupported blocks, `Match` rejection, excluded commands, Include references, invalid/unrepresentable values and an empty import result.
- Verify the parser reports exclusions and never interprets command-like data as execution; use harmless fixture-local side-effect markers to observe that `Match exec`, `ProxyCommand`, `KnownHostsCommand` and `LocalCommand` are not run.
- Place additional executable directives in nested Include fixtures and verify the source import does not read or evaluate their contents; do not add recursive-import behavior to make the fixture pass.
- Through the real import workflow, compare the original source contents before and after success and failure; change or remove the source after import and connect using the unchanged persisted snapshot.
- Connect real fixtures using imported endpoint, SSH user, key, IdentitiesOnly, compatible algorithm/cipher selections and registered Jump Server routes; observe actual destination, authentication and route rather than comparing generated formatting alone.
- Put conflicting endpoint, key, Host Key files and commands in the user's SSH configuration; exercise the master and every consumer and observe that those values and commands cannot affect runtime behavior.
- Use real OpenSSH self-checks only against generated configuration and test registered-route acceptance and unregistered-route rejection.
- Exercise every forced security invariant with observable outcomes: unknown/mismatched Host Key rejection, no alternate trust-file authorization, no local command execution, no automatic Host Key updates, application-owned control sockets and no independent control persistence.
- Compose with ADR-0003 to prove config Import grants no trust and does not read user Host Key entries; separately prove generated Host Key artifacts are used at runtime.
- Exercise read/validation/storage/configuration failures through the application workflow without fallback to external configuration or misleading saved/connected success.
- Use real GTK smoke coverage for keyboard access, loading, empty results, exclusion explanations, actionable errors and stale observations while asynchronous work is pending.
- Use isolated container filesystems for any disk-full generation/storage failure injection; never fill the host filesystem.

Generated-config unit tests from product §16.1 supplement these behavior checks; snapshots of whitespace or source-text inspection alone are not acceptance evidence.

## Out of Scope

- Executing or fully emulating arbitrary OpenSSH user configuration semantics.
- Recursive Include import, `Match` evaluation, arbitrary command-backed proxy routes or adding new directives to the accepted whitelist.
- Re-import/diff, automatic synchronization, watching original configuration files or a migration/merge design for later external edits.
- Rewriting the user's SSH configuration or Host Key files.
- Host Key Adoption, Verification, TOFU, trust replacement/deletion and trust-store implementation owned by ADR-0003.
- Master/session lifecycle and detailed authentication prompting owned by ADR-0001, beyond enforcing the shared configuration boundary.
- Full inventory/group-management UX, file/service management, metric handling or Operation-engine implementation.
- New runtime APIs, schema changes beyond the accepted model, alternate SSH libraries or platform expansion.

## Further Notes

This specification describes accepted future behavior, not functionality already present in the executable.

Product §4.4 compresses the control options as `ControlMaster`/`ControlPath`/`ControlPersist=no`.

Reading all three as `=no` would contradict the required single ControlMaster and application-owned control socket in product §§4.3 and 4.7 and ADR-0001.

The integrated interpretation is application-controlled `ControlMaster`/`ControlPath` with `ControlPersist=no`; this preserves both accepted invariants without selecting a new master-launch design.

The accepted import whitelist names key-algorithm/cipher settings as a category rather than an exhaustive list of individual OpenSSH directive spellings; this spec does not expand that category into a new compatibility promise.

The accepted sources do not define complete support for wildcard Host patterns, token/environment expansion or every OpenSSH precedence rule; the static parser must report unsupported/unrepresentable values rather than secretly evaluating the original file.

Algorithm choices remain subject to actual system OpenSSH and remote-server capabilities, not a guarantee that every requested algorithm is available.

No separate config publication blocker is established by these sources; implementation depends on the configuration, route and trust contracts of the connected epics.

# Design

## Usage

1. **Inspect saved settings without a connection:** bootstrap obtains actual E6 Store and calls `Configuration::spawn(store)`. GTK asks `configuration.inventory().await?`; E1 asks `configuration.resolve(server_id).await?` before trust, then reads `inspect_resolution`, `inspect_identity` and `inspect_endpoint` as needed. No source configuration is evaluated.
2. **Save references or explicitly import:** GTK sends `configuration.change(ConfigurationChange::SaveAuthProfile(draft)).await?`, SaveServer or Import. Approved E1 supplies the closed environment policy below. Store accepts only Configuration-created InventoryCommit and reads `inventory_write_view`; presentation distinguishes committed results from exclusions and failures.
3. **Compile an internally reserved start:** after resolve, E1 obtains E3 PreparedStart and consumes `into_prepared_start`, preserving the original resolution/reservation. It calls `configuration.compile(resolved, trust, reservation, prefixes).await?`; only the E1 private worker receives the sealed result and uses `launch_view`. Consumers retain generated fail-closed attachment policy.

All identity fields and InventoryCommit/CompiledConfiguration authority data remain private. Immutable views have explicit readable fields; Store and launch accept wrappers, never views. StartReservation, CompiledConfiguration and TrustStart are not Clone. Identity equality/hash uses full effective target and ordered hop authentication values, excluding UUID/display/group/tags/environment; no DNS-equivalence guessing.

`environment_discriminator` is the byte-preserving legacy observation in Server and untrusted boundary input in ServerDraft, not an open new-write enum. Configuration validates every new stored value through ClosedEnvironment and serializes its exact approved spelling into the existing `servers.environment` field. No public actor signature or existing record field changes. Accepted non-secret profile references/negotiation values use the existing auth_profiles/settings schema; no secret/new schema is implied. Configuration is the semantic inventory writer; E6 Store only applies its sealed validated commit. All declarations are initially introduced by ADR-0006:01 in their canonical modules; owner-method tickets below implement actual runtime production, not a type-only capability claim. GTK adapters remain private, use glib::MainContext delivery, and do not put widgets in public application signatures.

- **Reads:** ConfigurationChange, ServerDraft, AuthProfileDraft, InventorySnapshot.

### Ordered flows

1. **Saved inventory and resolution (01):** external E6:01 compatible primary Store → `Configuration::spawn`; external saved Server identifier → `Configuration::inventory` returns actual InventorySnapshot → `Configuration::resolve` constructs complete ResolvedConnection → `inspect_resolution` → `inspect_identity` → `inspect_endpoint` supply borrowed views. Persisted rows are real external inputs from Store, not fabricated seed data. No SSH/trust work occurs.
2. **Save/import (02 → 03):** approved E1 environment policy → external profile/Server drafts or explicitly selected source path → `Configuration::change` validates the closed environment and references and statically parses the whitelist, recording all exclusions → private InventoryCommit → `InventoryCommit::inventory_write_view` inside external E6:01 Store request → all-or-none expected-revision commit → ConfigurationResult and truthful GTK result. Source files remain unchanged, imported startup preference false, and no key is adopted. Rejected environment input is never a permissive fallback.
3. **Direct compilation and attachment (01 → 04):** external E1:02 runtime control calls `resolve` first; external E1:02 reservation (declaration E6:01) plus E3:04 gate returns original owned inputs and fresh TrustStart → E1 consumes PreparedStart → `Configuration::compile` validates binding, writes forced policy and self-checks only generated input → `CompiledConfiguration::launch_view` supplies borrowed launch material while E1 retains wrapper-only launch authority. External E1:02 terminal and E1:03 SFTP/Operation/Collector exercise the same generated attachment boundary, never autonomous fallback.
4. **Full registered route (03 → 04 → 05):** saved route/imported registered entries from change and complete identity from resolve → compile privately refines routed aliases using matching E1-issued prefix generations (external E1:04 at execution, not a prerequisite to writing configuration) → generated-only ssh -G verifies every hop and rejects UnregisteredProxyRoute → external E1:04 actual multi-hop transport reaches only the registered target. E3:04 trust still gates each prefix. Generation/storage/self-check failure yields no launch capability or fallback; GTK receives glib::MainContext loading/error/stale updates.

## Decision

- Select Sol's deep Configuration actor with private identity construction and sealed Store/launch boundaries.
- Integrate original-reservation handback and immutable purpose-specific projections from repaired Sol; no raw directive-map or generic persistence authority.
- Reject Terra's whole worker-process shape: extra ownership/failure boundaries do not improve this local configuration boundary.
- Accept generated-only OpenSSH self-check cost for observable runtime isolation. Operator approval selects E1's five closed environments with strict new-write validation and preservation of legacy observations.

### Approved E1 environment policy

The operator approved E1 on 2026-10-31. This is documentation decision completion, not an implemented inventory feature.

| ClosedEnvironment | Exact persisted string | Meaning                                       |
| ----------------- | ---------------------- | --------------------------------------------- |
| Unspecified       | `unspecified`          | The operator has not classified the Server.   |
| Development       | `development`          | Development and experimentation.              |
| Test              | `test`                 | Repeatable testing or continuous integration. |
| Staging           | `staging`              | Pre-production validation.                    |
| Production        | `production`           | Live workloads.                               |

The new Server form selects Unspecified. Static import assigns Unspecified because its whitelist contains no environment directive. A valid explicit selection replaces that default. Neither workflow infers an environment from a name, host, group, tag, comment, Include file, process environment, or unrelated Server. Existing ServerDraft remains a concrete raw boundary value. This approval creates no JSON API or protocol-level omission rule.

Every supplied new-write value must exactly match one persisted spelling. Empty strings, whitespace, aliases, different casing, unknown strings, and any explicit null supplied by an input boundary are field-specific ValidationError. Configuration does not trim, case-fold, or coerce them. The rejected save persists nothing. Once validated, every new stored value maps to ClosedEnvironment. An edited legacy Server requires the operator to choose a valid member before saving that Server.

Inventory reads preserve actual existing discriminator bytes. Exact matching spellings can display their member without a rewrite. Nonmatching values, including an existing empty string, remain visible as unclassified legacy values with raw details, not Unspecified. The String-only observation does not fabricate support for missing or NULL metadata. If that representation cannot read the actual schema or value, inventory reports StorageError rather than inventing an empty string or a successful missing-value observation.

Migration preserves all existing values transactionally or returns StorageError. Cancellation preserves the legacy row. Editing another Server or Auth Profile cannot normalize it. Otherwise valid legacy Servers remain resolvable with a visible classification warning. Environment never changes structural Connection Identity equality, credentials, trust, confirmation, or Operation authority. Ambiguous commit delivery requires an actual inventory revision read, not automatic replay or false import success.

`Configuration::inventory`, `resolve` and `change` retain their signatures. Their postconditions include the preservation, metadata-only resolution and closed new-write rules above. Usage 2 and ordered flow 2 consume this approved policy. Ticket 03 owns the first new-write and import proof; 01 owns truthful existing reads.
